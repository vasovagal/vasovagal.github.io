# Vagus timing anatomy — 2026-08-19

Aggregate-only timing record for the public “How so smart?” page. No private note title, path, query, label, body, or ranked result is included.

## Environment

- Vagus: `v0.13.0` (`260c23a1c0457bdc8839fe0050ee7c3e865a2e35`)
- Machine: Apple M1 Pro
- Search corpus: 566 Markdown files, 5,022 chunks
- Embedder: `google/embeddinggemma-300m`, 768 dimensions
- Semantic backend: exact cosine (automatic below 10,000 embedded chunks)
- Model files were present locally (no network); each sample was still a separate no-daemon CLI process, and later repetitions could benefit from the operating system's file cache

These are explanatory local measurements, not portable latency guarantees.

## Search timing

Five separate invocations used the fixed, non-private query `local search architecture`, discarded result output, and enabled Vagus's internal stage timer. `--no-index` isolated retrieval from the automatic incremental refresh.

Representative command:

```sh
vagus search 'local search architecture' --mode hybrid --timings --no-index >/dev/null
```

Median of five runs:

| Search path | Retrieval (including RRF for hybrid) | Result hydration (reported `fuse` timer) | Reranker load | Reranker compute | Core total |
|---|---:|---:|---:|---:|---:|
| BM25 only | 2.1 ms | 0.9 ms | — | — | 4.1 ms |
| Vector only | 985.0 ms | 0.9 ms | — | — | 986.9 ms |
| Plain hybrid | 1,074.0 ms | 0.9 ms | — | — | 1,075.8 ms |
| Hybrid + rerank, context 0 | 1,010.0 ms | 0.9 ms | 132.6 ms | 953.9 ms | 2,089.7 ms |

Stage medians do not need to sum exactly to the median total. For the plain path, Vagus's `retrieval` timer includes BM25, embedder construction/query inference, exact vector retrieval, and RRF; it does not currently split those substeps. The separately named `fuse` timer currently covers result hydration after ranking. The BM25-only comparison and RRF's tiny rank-list arithmetic make the dominant cost clear: local model work.

The core timer starts inside retrieval. It excludes shell/process launch, automatic indexing (disabled here), and any downstream agent reasoning. Normal `vagus search` first performs an incremental vault refresh; an unchanged mtime fast path does not load the document embedder.

## Changed-note indexing timing

Index measurements used an isolated temporary vault and data directory, sharing only the already-cached model files. Five synthetic notes contained five Markdown sections and repeated non-personal explanatory prose. Each note was filed through the real timed path:

```sh
vagus file '00-Inbox/synthetic-N.md' \
  --to '10-Projects/Timing' --stats --json
```

Median of five runs:

| Indexed phase | Median |
|---|---:|
| Total file + incremental index path | 1,878.0 ms |
| Document embedding inference | 794.2 ms |
| Tantivy commit + merge wait | 83.9 ms |
| Chunking | 0.062 ms |
| SQLite chunk replacement | 0.274 ms |
| Tantivy document addition | 0.020 ms |
| Embedding/vector insertion | 1.417 ms |
| Frontmatter enrichment | 0.329 ms |
| File move | 0.112 ms |

The median per-run residual after exposed phase timers was about 1,017 ms. This is honest subtraction rather than a separately instrumented phase: it includes embedder initialization plus vault snapshot/open and vector-index persistence/orchestration. Phase medians do not sum exactly to the median total.

The important architectural distinction is qualitative and stable:

- Every incremental run snapshots Markdown paths and mtimes so additions and deletions are reconciled.
- An unchanged note takes the fast path and does **not** load the embedding model.
- New, changed, incomplete, or explicitly refreshed notes pay parse/chunk/embed/write work.
- Full rebuild time is therefore dominated by local document embedding; ordinary no-op refresh is not.
